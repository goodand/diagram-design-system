> 추상적이고 단순한 그래프 표현에서 시작해 사용자가 더 보고 싶은 부품을 확대하면 더

## 1. 노드 타입 넷

| # | 타입 | 무엇을 지시하나 | 판별 규칙(기계) | 렌더 |
|---|---|---|---|---|
| 1 | **자료** Datum | 실물 값 하나 — 「개는 갯과이다」 · `개 is_a 갯과 · ev1` · `revision 1` · `3 × PASS` | 입력·출력 레지스터를 **갖지 않는다**(값 자체가 내용) | **원형(pill)** · **채움** · 호박 — §12.1 #2 가 지정한 모양이라 바꾸지 않는다 |
| 2 | **작업** Task | 입력을 출력으로 바꾸는 변환. 이름은 **명사형 사람 말** | `IOT` 삼항을 빈 칸 없이 채운다 — 생성기가 단언(R7) | **직사각** · **투명** · 계열색 테두리(§4) — §12.1 #2 |
| 3 | **구현** Implementation | 그 작업을 실제로 수행하는 저장소의 물건 — 함수 · 규칙표 · 사전 · 고정판 모델 · 외부 실행체 | 이름이 **코드 식별자**(고정폭으로 쓴다) | 파란 글씨 · 상자로 그릴 때는 **직사각 채움**(N3 — 코드가 있으므로) |
| 4 | **표지** Marker | 노드가 **아니다** — 노드에 붙는 상태. `제품면 밖` · `여기 없음(실행 위치)` · `후보(판정 전)` · `이 그림의 주장이 걸린 자리` | 자기 이름을 갖지 않는다(항상 다른 노드에 붙는다) | 회색 · 점선 테두리 · 강조색 · 빈 칸 |

**1:1 이면 상자를 나누지 않는다.** 한 과업의 구현이 하나뿐이면 위·아래 두 상자가 같은 낱말을
반복하므로, **한 상자의 위·아래 칸**으로 합친다(위 = 자료·과업·출력, 아래 = 코드 이름과 *무엇을
하는가*). 구현이 **둘 이상일 때만** 아래로 편다 — 그때 아래 상자들은 「핵심 구성」이고 그것도
이름이 과업이다. 사용자 지시(2026-09-06): *「1:1 대응인 부분은 표시 자체를 할 필요가 없어 보인다 ·
1:1 이면 Task 의 설명을, 1:N 이면 핵심 구성들을 — 모두 Task 로 이해할 수 있도록」*.

**왜 표지를 노드로 두지 않는가.** 초판에서 「증폭 루프」를 호박으로 칠했다가 그 상자가
자료로 읽혔다(2026-09-06, 사용자 지적 — 회고 G391). 표지를 타입으로 올리면 같은 상자가
두 타입을 갖게 되고, 그때 색은 아무 뜻도 없어진다. 표지는 **타입이 아니라 형용사**다.

## 1.5 노드 부호 체계 — Core 4 (사용자, 2026-09-06: "Core 축만 정해도 될 것 같다")

간선과 같은 방식이다: 칸을 채우기 전에 **축의 뜻**을 건다. 노드의 Core 는 두 축 × 2 = 4 칸이고,
간선의 Core 처럼 **빈 칸이 없다**.

**순서와 유도 관계.** 사용자가 먼저 청한 것은 관계(「선」)였고 노드(「면」)는 그 뒤다 — 그리고 면은
선에서 **유도**됐다. **면의 테두리는 선이다**: 노드의 둘째 축(테두리 실/점)은 간선의 선 축을 그대로
물려받았고, 그래서 두 체계에서 실선/점선의 뜻이 같다(실물·확정 / 절차·비확정). 새 축을 지어낸 것이
아니라 있는 축을 면의 경계에 적용한 것이다. 「1:N 이면 1 부터」의 또 한 사례 — 선이 1 이고 면은
거기서 나온다. 노드의 첫째 축(모양)만 면 고유의 축이다.

| 축 | 값 | 뜻 |
|---|---|---|
| **모양** | 원형 / 직사각 | 원형 = **있는 것**(자료 · 개념 · 형태소) · 직사각 = **하는 것**(과업 · 작업 항목 · 모듈) |
| **채움** | 채움 / 투명 | 채움 = **구체**(값이 있는 자료 · 코드가 있는 구현) · 투명 = **추상**(개념 · 과업) |

| Core | 모양 | 채움 | 뜻 | 지금 쓰는 곳 |
|---|---|---|---|---|
| N1 | 원형 | 채움 | **자료** — 값이 있다 | 예시 자료(슬라이드 16 · 기제 9) — 호박 채움 |
| N2 | 직사각 | 투명 | **과업** — 변환, 값이 아니다 | 파이프라인 과업 41 · 목적 노드(자두 테두리) |
| N3 | 직사각 | 채움 | **구현** — 코드가 있다 | dependency 모듈 상자 · 시각판 그림 1 · 적용판 |
| N4 | 원형 | 투명 | **개념** — 값이 아니라 뜻 | 개념 그래프 ellipse 95 |

**둘째 축이 테두리에서 채움으로 바뀐 경위(2026-09-07).** 첫 판은 테두리(실선 = 실물 / 점선 = 절차)였고 자료와 개념이 한 칸(N1)이었다.
사용자: *「박스들의 점선/실선 차이도 직관적이지 않고, 원형처럼 안에 있는 면의 색을 투명하게 하는 것도 괜찮아 보이네 … 이렇게만 봐도
원형이 훨씬 대조가 잘 되네」* — 원형 칸은 이미 채움(자료)/투명(후보)으로 갈려 읽혔고, 상자는 둘 다 채워져 점선 하나로만 갈려 안 읽혔다.
채움을 축으로 걸자 **자료와 개념이 갈라지고**(채움/투명) 뜻도 더 직관적이 됐다(채워진 것 = 손에 잡히는 것). 점선 테두리는 축에서 빠져
「후보·비확정」 **표지**로만 남는다(예: 규칙 판정 전 자료 = 채움 + 점선). 부재 = 투명 + 글자 없음 + 회색 — 그대로.

**Main 의 첫 결정(같은 날, 사용자 제안)**: 수직 관계(목적/수단·전체/부분)의 양 끝이 같은 상자로 보여 관계가 묻혔다 → ① **목적 노드는 고유색
테두리**(자두 `#6b4e8a`) ② **부분은 전체보다 연하게** — 투명 상자는 테두리 농도로, 채운 상자는 채움 농도로(「층은 구체화의 깊이」의 시각판).
선의 색 축(판정)과 층이 달라 충돌 없다.

**가장 범용적으로 그려진 노드**(2026-09-06 계수, `docs/formal/*.dot` + `docs/diagrams/*.dot` 26장 +
손 SVG 3종): **직사각 289**(box 212 + 슬라이드 41 + 기제 18 + 시각판 18) 대 **원형 124**(ellipse 95 +
16 + 9 + 4). 그 외 `note` 13(목적 문장 — 특수 표지) · `octagon` 5 · `plaintext` 2 는 **Sub**(계열이
선언하는 모양)이고, Core 두 모양이 전체의 96% 를 덮는다.

**§1 의 네 타입과의 관계.** 자료 = N1 · 과업 = N2 · 구현 = N3 · 개념 = N4 이고, **표지는 노드가 아니므로 칸이
없다**(회색·빈 칸·점선·강조로 N1~N4 에 붙는다). §1 이 "무엇을 지시하나"로 가른 것을 이 표는 **두 축의
값**으로 다시 얻는다 — 같은 분류가 두 방향에서 나오면 그 분류는 안정적이다.

**이 표로 다시 본 것 둘**: ① 슬라이드의 구성 상자는 첫 줄이 코드 이름이라 구현처럼 보이지만
**구현 레지스터를 가진 과업**이다(굵은 줄이 사람 말 Task 이름) → N2 점선이 맞다. 순수 구현 상자(N3
실선)는 dependency 의 모듈 상자와 시각판 그림 1 에만 있다 — 생성기는 `box(role="impl")` 로 그릴 수
있게만 두었다. (처음엔 첫 줄 철자로 갈라 둘을 실선으로 만들었다가 되돌렸다 — 철자는 타입이 아니다.)
② worklane 의 작업 항목 상자는 절차인데 실선이다 — 그 계열 문서가 자기 범례로 선언한 것이라
**Sub 로 기록만** 하고 바꾸지 않는다.

**Main 축 하나가 확인 대기다 — 채움**(사용자 제안 2026-09-07: *「전체/부분에서 부분색을 더 연한 것을 적용해야 하나?
목적도 다른 색상을 사용하고」*). 후보 규칙 둘: ① **채움 농도 = 구체화 깊이** — 전체는 진하게, 부분은 연하게(「층은 구체화의
깊이」와 같은 결) ② **목적 노드는 고유색**(자두 `#efe7f3/#6b4e8a`) — 과업·자료·개념·회색 어느 것과도 겹치지 않고, 선의 색
축(판정)과는 층이 다르다(노드 채움 vs 간선 색). 적용판 「선과 면」에 먹여 놓았다(적용 1 · 격자 C3/C4 · 대조 (2)(3)); 확인되면
슬라이드 생성기(`_fan` 자식 상자·목적 상자)에도 건다. 나머지 Main 후보(크기 · 묶음)와 Sub(`note`·`octagon`)는 그대로 미정.

## 2. 관계 타입 셋 — 그리고 층은 노드의 성질이 아니다

| 관계 | 무엇을 잇나 | 방향 | 렌더 |
|---|---|---|---|
| **예시 흐름** | 자료 ↔ 작업 | 있다 | 실선 · 곡선 · 화살표 |
| **파이프라인 흐름** | 작업 → 작업 (순서) | 있다 | 굵은 점선 · 직선 · 화살표 |
| **구체화**(전체/부분) | 작업 → 그 핵심 구성 | 배치가 나른다 | 가는 **실선** · 직각 · **화살촉 없음** · 기본색(C4, 존재 관계) — **하나의 관계로 고정**: 그려진 것은 전부 `component_of` 꼴 |

**구체화에 화살촉이 없는 이유**(사용자 지시, 2026-09-06): 구체화는 데이터가 흐르는 것이
아니라 *같은 것을 더 자세히* 보는 것이라 방향이 없다. 화살촉은 흐름 전용이다.

**층(L0/L1/L2)은 노드의 타입이 아니라 구체화의 깊이다.** 같은 작업 노드가 L0 에도 L1 에도
설 수 있다 — 8단계 「독립 재검증」이 실물이다. 층 라벨은 그 노드가 구체화 사슬의 어디에
놓였는지를 **읽어 낸 값**이지 노드가 들고 있는 성질이 아니다. 이 구분을 잃으면 "L2 노드"
같은 말이 생기고, 그때부터 같은 함수가 어떤 그림에서는 L1 이고 어떤 그림에서는 L2 인
모순을 설명할 수 없다.

이것은 이 저장소가 이미 비싸게 배운 것과 **같은 형태**다: 격 라벨(문장 토큰 사이)과 개념
관계(개념 사이)는 층이 달라서 같은 등록부에 넣을 수 없었고, Lean 타입 검사가 그것을 거부했다
(`../formal/L1_ontoclean.lean` `CaseLayer`, 정본 §7-4). 층이 다른 것을 같은 관계로 이으면
그림에서도 타입 오류다.

## 2.5 간선 부호 체계 — Core 4 · Main 8 · Sub 10 (사용자 규약, 2026-09-06)

사용자: *「곡선/직선 2, 없음/단방향 2, 실선/점선 2 — 이렇게 8가지가 Main. 나머지 10가지는
sub 로, context 에 따라 역할을 여러 가지 부여하는 것도 가능하다.」* 이어 *「Core 는 직선 1 ×
없음/단방향 2 × 실선/점선 2 로 4가지」*. 그리고 *「확정적인 것, 1:N 이면 1 에 해당하는 것을 먼저
결정하라」* — 여기서 「1」은 **축의 뜻**이다. 칸 18개는 용량이고, 축마다 뜻을 하나만 걸지 않으면
어느 칸이든 「같은 표시 두 뜻」이 된다.

세 층이다. **Core 4**(직선만)는 가장 확정적이라 **빈 칸이 없다** — 네 칸 전부 뜻을 갖는다.
**Main 8** 은 Core 에 곡선 넷을 더한 것이고 거기서부터 미정의 칸이 나온다. **Sub 10** 은 문맥이
선언한다. 미정의는 안쪽 층에 없고 바깥 층에만 있다 — 「확정적인 것 먼저」가 층 구조로 나타난 것.

### Core 4 — 직선 × 촉(없/단) × 선(실/점). 전부 정의됨

| Core | 촉 | 선 | 뜻 | 지금 쓰는 곳 |
|---|---|---|---|---|
| C1 | 단 | 실 | **확정된 방향 관계** | 해석된 개념 관계(`is_a`·`part_of`…) · worklane 실측 의존 · 최상위 import |
| C2 | 단 | 점 | **절차, 또는 판단으로 그은 관계** | 파이프라인 순서 · worklane 판단 의존 · lazy import |
| C3 | 없 | 점 | **목적/수단**(행위 · 수직) | HANDOFF §0.5 목적 사다리 — 그릴 자리 |
| C4 | 없 | 실 | **전체/부분 = 구체화**(존재 · 수직) | L0→L1→L2 (2026-09-07 부터 실선) |

### Main 8 = Core 4 + 곡선 4 — 전역 고정 (계열이 달라도 같은 뜻)

| # | 선형 | 촉 | 선 | 전역 뜻 | 지금 쓰는 곳 |
|---|---|---|---|---|---|
| 1 | 곡 | 단 | 실 | **자료가 움직인다** | 예시 흐름 |
| 2 | 곡 | 단 | 점 | 자료가 움직이되 **비확정**(후보) | *미정의 — 후보: 증폭 출력* |
| 3 | 곡 | 없 | 실 | — | **빈 칸** |
| 4 | 곡 | 없 | 점 | — | **빈 칸** |
| 5 = C1 | 직 | 단 | 실 | (Core 표) | |
| 6 = C2 | 직 | 단 | 점 | (Core 표) | |
| 7 = C4 | 직 | 없 | 실 | (Core 표) | |
| 8 = C3 | 직 | 없 | 점 | (Core 표) | 대칭(동치·disjoint)은 Sub 로 |

**이 표가 §5 의 계열 충돌을 푼다.** worklane·dependency·파이프라인 세 계열은 Main 8 안에서
충돌하지 않는다 — 내가 "같은 점선, 다른 뜻"이라고 적었던 것은 전부 **Sub 층의 차이**였다
(worklane 의 파선「판단」과 점선「선택적 재사용」은 둘 다 Main 6 이고 넓은/좁은 점선이라는 Sub 값으로
갈린다). 빈 칸 3·4 는 정의하지 않은 채로 둔다 — 자리를 채우지 않는 것도 규약이다(§12.1 #3).

### 색 — 18 밖의 겹침 층, 뜻은 **판정 3값**

| 색 | 뜻 | 목적 문장의 절 |
|---|---|---|
| 기본(검정/잉크) | 성립함 · 정상 | 「성립함을 판정하거나」 |
| 회색 | **판단 불가** — 미해석 relation · 여기 없다(실행 위치) | 「판단 불가를 그 종류와 함께」 |

색 축이 판정이므로 **구체화 선의 파랑은 뺐다**(2026-09-06) — Main 8 = 직·없·점 만으로 유일하다.
파랑은 **구현 노드의 글씨**에만 남고, "파란 것 = 구현"은 그대로다.

### 구조 부류 — 관계는 뜻이 아니라 그래프 성질로 가른다 (사용자, 2026-09-06)

사용자: *「(1) 실행흐름 (2) 추상→구체 (3) 목적/수단 (4) Before/After (5) 문제/해결 (6) 없음/있음
(7) is_a (8) has_a (9) 기표/기의 … (1-3)은 연속적일 수 있고 … 개념적인 것들은 다루지 않고 DAG 같은
graph 이론에 따라서 관계를 세분화하는 것이 더 적절할 수 있다.」* 이것이 도식 문법을 제품과 **같은
어휘**로 묶는다 — 파이프라인의 관계 게이트가 판정하는 것이 바로 그래프 성질(비순환·반대칭·추이·배타)이다.

| 구조 부류 | 성질 | 아홉 중 | 우리 게이트 |
|---|---|---|---|
| **순서 · 사슬**(전순서) | 유향 · 추이 · 비순환 · 다음이 하나 | (1) 실행 흐름 · (3) 목적 사다리 | 파이프라인 `seq` — 구조가 강제 |
| **순서 · 나무/DAG**(부분순서) | 유향 · 추이 · 비순환 · 갈라짐 | (2) 구체화 · (7) `is_a` · (8) `has_a`/`part_of` | `relation.acyclicity` · `antisymmetry` · `isa_hasa_exclusivity` |
| **사상**(함수, 비추이) | 유향 · 다:1 · 합성이 뜻을 갖지 않음 | (9) 기표→기의(`denotes`) · 구현→과업 · 증거→주장 | `evidence_anchoring` · §7-4 지시≠포섭(Lean 타입) |
| **대비 쌍** | 그래프 관계가 아니다 — 두 칸의 **배치** | (4) Before/After · (5) 문제/해결 · (6) 없음/있음 | 간선 문법 밖. (6)은 이미 「부재 = 빈 칸」으로 노드 상태다 |

**따라오는 것 셋.**

1. **(1)(2)(3)이 "연속적일 수 있다"는 것이 곧 추이성이다.** 셋은 뜻이 달라도 구조가 같고(유향·추이·
   비순환), 차이는 노드 종류(과업 / 추상 층 / 목적)와 가지 수(사슬 vs 나무)뿐이다. 그래서 셋이 도식에
   가장 많이 쓰인다 — 같은 기하(한 방향으로 흐르는 배치)로 그려지기 때문이다.
2. **촉 축의 뜻을 정정한다.** 촉 없음 = 무방향이 아니다. 구체화는 **유향 나무**(부모→자식)인데 촉이
   없다 — 방향을 화살표가 아니라 **배치**(위 = 추상)가 나른다. 정확한 뜻: 촉 있음 = 방향을 화살표가
   나른다 · 촉 없음 = 방향이 없거나 **배치가 나른다**. C4(직·없·실 = 대칭)만 진짜 무방향이다.
3. **구체화는 도식에서 하나의 관계로 고정하고, 그 하나는 전체–부분이다.** 사용자(2026-09-06):
   *「구체화는 is_a·has_a 등 여러 가지로 표현될 수 있긴 한데 도식화할 때는 하나의 관계로 고정하는
   것이 좋다 … 현재 slide 에서는 구체화가 전체와 부분의 관계에 가깝다.」* 실측도 그렇다 — 그려진
   구체화 간선은 전부 L0 과업 → 그 「핵심 구성」이라 **`component_of` 꼴**이고, is_a 꼴(L1 이 L0 의
   한 종류)은 한 번도 나오지 않는다. 그래서 구체화 = **전체–부분**으로 읽고, 다른 꼴이 필요하면 그것은
   개념 그래프 계열의 일이다(등록부가 촉 모양으로 나른다). 구체화에는 Sub 변종을 두지 않는다.

**순서 부류의 검사는 구체화에도 걸린다.** `has_a`·구체화가 같은 구조(부분순서)이므로 `part_of` 에
걸리는 비순환·반대칭이 구체화 사슬에도 성립해야 한다(L0→L1→L0 은 오류). 지금 생성기의
`assert len(fanned) <= 1` 은 그 검사의 아주 약한 판이다 — 후보로 둔다.

### 개념 관계(`is_a` · `has_a` …)는 이렇게 그린다 — 등록부가 「1」

파이프라인 도식에서 개념 관계는 **자료 노드의 값**(「개 is_a 갯과」는 글자)이고 간선이 아니다. 간선으로
그리는 것은 **개념 그래프 계열**(정본 지식 그래프 `L1_GOAL_KG_render.dot`, 노드 = 개념)이고, 그 문법은
`scripts/l1_s5_model.edge_code` 가 **등록부에서 유도**한다 — 그림이 종류를 고르지 않는다:

| 등록부 `feature_type` | 종류 | Main | Sub 촉 모양 | 근거 |
|---|---|---|---|---|
| `essential_feature` | `is_a` | C1 (직·단·실) | **빈 삼각** `onormal` | UML 일반화 |
| `structural_composition` | `component_integral` · `portion_mass` · `stuff_object` | C1 | **마름모** `diamond` | UML 합성(부분이 전체에 속함) |
| `structural_composition` | `member_collection` · `subcollection` | C1 | **빈 마름모** `odiamond` | UML 집합(구성원은 독립 존재) |
| `locational` · `contextual_usage` | `place_area` · `ufo_phase` | C1 | 보통 촉 + 라벨 | **미결** — 덜 확정적이라 기본값 |
| (등록부 밖) | `has_a` 원문 등 미해석 | — | 촉 없음 · **회색** · 점선 | 판단 불가 — 방향도 주장하지 않는다 |

방향은 등록부 `claim_subject` 가 준다(부분 → 전체, 하위 → 상위) — 그래서 마름모는 전체 쪽에,
빈 삼각은 상위 쪽에 앉는다(UML 과 같은 자리). 순환·충돌은 **붉음**으로 — `SEMANTIC_CYCLE` 은 두
간선이 각각 붉어진다(한 간선의 양방향 촉이 아니라). 라벨은 그대로 `종류 | claim | 검증기 | 표시 | 의미`.

**앞 판의 결함 둘**을 이 표가 고쳤다: ① `is_a` 만 실선이고 나머지 8종이 전부 같은 파랑 점선이었다
(`component_integral` 과 `place_area` 가 구별되지 않았다) ② 그 파랑 점선이 파이프라인 계열의 구체화와
충돌했다. 계약 `test_l1_s5_model.py::test_kg_dot_edge_code_*` 가 고정한다.

## 2.6 의미의 Core — 확정 (사용자, 2026-09-07)

표현의 Core(§1.5 면 4 · §2.5 선 4)를 정한 것은 의미를 정한 것이 아니었다 — 칸에 적힌 것은 용례였다.
사용자 규약: *「표현은 시각화하여 사용자의 확인을 받아야 하고 … 의미의 Core 는 4가지밖에 정할 수 없고
4가지를 결정해야 한다. 정체성과 식별성을 모두 드러내야 한다」*, *「이것은 의미를 분류하고 그 의미에 어떤
표현을 매핑할 것인지 결정하는 의사결정이며 의사소통이다」*. 후보를 그림으로 세 판 올려(`../formal/design_system_demo.html`
「의미의 Core 4」) 확정했다. **색은 Core 와 독립**(겹침 층, 판정 3값).

### 선 — 네 의미와 그 표현

사용자 확정: *「(1) 실행흐름 (2) 전체/부분 (3) 목적/수단 (4) is_a 까지 의미의 Core … 한 줄뿐 아니라 tree 로
표현할 수 있어야 한다」*. 축의 뜻: **방향성** = 수평(화살표가 방향) / 수직(배치가 방향). **연속성** = 실선 =
**존재(구조) 관계** / 점선 = **행위(의도·시간) 관계** — 3판의 「실선 = 나무 / 점선 = 사슬」은 흐름·목적이 tree 로
갈라지는 것을 막아서 버렸다. **두 줄 다 사슬로도 tree 로도 그린다.** 이 축은 면의 모양 축(있는 것/하는 것)과 같은 결이다.

| | 수평 · 촉 단 | 수직 · 촉 없(배치) |
|---|---|---|
| **실선 = 존재** | 분류 `is_a` → C1 — *A 는 B 의 한 종류다* | **전체/부분** → C4 — *A 는 B 를 이루는 부분이다* (구체화) |
| **점선 = 행위** | 실행흐름 → C2 — *A 가 끝나면 B 가 시작한다* | **목적/수단** → C3 — *A 는 B 를 위해 있다* |

식별성은 인접 칸과의 차이 둘로 적힌다(대각선은 두 축이 다 다르다). 넷째로 고르지 않은 기표/기의(지시)·대칭(동치·disjoint)은
**Sub** 로 내려간다. 따라온 변경은 하나 — **구체화(전체/부분) 선이 점선 → 실선**(존재 관계). 촉 없음·직각·기본색은 그대로.
생성기 `_fan`·시각판 `.spec`·적용판에 적용했다(2026-09-07).

### 의미별로 하나씩 — 시각 대조를 위한 네 그래프, 전부 DAG (사용자 요구, 2026-09-07)

*「네 가지 모두 DAG 로도 표현할 수 있다는 것을 보여야 한다 — 각각을 적용한 사례를 포함시켜라 … 시각적인 대조를
확인하기 위함이다.」* 그래프마다 **관계 하나만** 그린다(is_a 만 보이는 그래프, 전체/부분만 보이는 그래프) — 넷을 나란히
놓았을 때 표현이 서로 구별되는지 눈으로 확인하기 위해서다. 노드마다 관계 하나씩 섞은 범례(「적용 2」)와는 목적이 다르다.
그림은 `../formal/design_system_demo.html` 「의미별로 하나씩」, 출처는:

| 의미 | 실례 | 출처 | DAG 인 이유 |
|---|---|---|---|
| 실행흐름 (C2) | 3단계 반대칭·비순환·배타 ∥ → 판정 행 변환 | `gen_goal_slides_l12.py` 3단계 `edges1=[(0,3),(1,3),(2,3)]` · `s5_verify.py` 검사 6 → PASS | 갈라졌다 합류 — 한 줄로 그리면 거짓 순서 |

주의: `classify_owl` 의 stereotype 은 gufo 클래스를 **rdf:type**(punning)으로 붙인다 — 둘째 `is_a` 부모가 아니다
(`cg_owl.py:437`). is_a 의 DAG 실물은 gUFO 자체에 있다. 나는 처음 stereotype 을 다중 상속으로 짚었다가 코드를 읽고 고쳤다.

### 면 — 두 구조 부류가 두 축

사용자: *「면에서는 사상, 대비 쌍 중에서 2가지 고르면 될 것 같고」*. 선이 순서 부류(사슬·나무)를 가져갔고, 남은 둘이 면의 축이다:
**사상** — 이 노드가 무엇을 지시하나(있는 것 / 하는 것) → 모양(원형/직사각). **대비 쌍** — 있음/없음(실물 / 절차·비확정, 부재 =
빈 칸) → 테두리(실선/점선). §1.5 의 N1~N4 가 이 근거를 얻는다. 선의 네 관계와 면의 네 노드가 **같은 구조 부류 넷**에서 나온 것이
이 체계의 뼈대다.

**통일하지 않는다.** 계열마다 재는 것이 달라서 같은 문법을 강요하면 어느 한쪽이 거짓이

한 표시에 한 뜻만 준다. evidence-evaluator 의 다이어그램 README 도 같은 방식으로
"어두운 배경 도구 해부도에서는 빨강이 거부 경로"라고 자기 예외를 적고 있다.

## 5.5 `IOT` 라는 이름 — 오늘 생겼다

사용자가 *"IOT 검색도 해봐"* 라고 했고, 코드 검색을 맡은 동료 세션이 코드 자산 색인 ·
`rg` 원문 · `git log -S` · `git log -G`(단어 경계)로 전수 조회했다. **결과: 약어 `IOT` ·
`I-O-T` · `ITO` 는 워크스페이스에 쓰인 적이 없다**(전부 0 — `-S"ITO"` 3건은 `EDITOR` ·
`MONITOR` 부분문자열 오탐이고 `-G` 토큰 경계로는 0). 실제 표기는 `input-task-output`
(문서 9곳)과 사용자 원문 `Input_data → Task → Output_data` 다.

그리고 그 어휘를 건드린 커밋 **5건이 전부 `.md`** 였다 — **규약은 문서에만 있었고 코드에는
이름이 없었다.** 이 계열의 삼항은 `gen_goal_slides_l12.py` 가 유일한 담지자인데 이름 없는
줄 리스트(`l1lines`)였다.

**시점을 못박는다**(동료 세션 자기 정정, 2026-09-06): 그 조회의 「0건」은 **HEAD 기준**이고,
같은 시각 우리 **작업 트리**에서는 이 이름이 만들어지는 중이었다 —
`git show HEAD:docs/formal/gen_goal_slides_l12.py | rg -cw IOT` → 0 · 작업 트리 `rg -cw IOT` → 4.
부재 판정에는 **어느 시점의 트리인가**를 붙인다. 이것이 A15(주장 범위가 확인 범위를 덮는다)의
시간 축 판이다.

그래서 이름을 줬다: `IOT = namedtuple("IOT", "given task yields")`. 이름이 생기자 검사도
생겼다(R7). **읽지 않는 필드는 주석과 같은 지위**(HARNESS_KNOWHOW D9)의 같은 형태이고,
이 규약이 코드에서 자기를 지킬 수 있게 된 첫 지점이다.

## 4.5 코드로 본 체계 전문 — 이 절이 `diagram_design.md` 다

규칙을 산문으로만 적으면 코드가 그것을 어겨도 아무 말도 하지 않는다(오늘 `IOT` 가 그랬다).
그래서 **체계의 모든 항목을 코드 표현과 함께 나열한다.** 정본은 코드이고 이 절은 그 색인이다.

### (가) 토큰 — 색

```python
# docs/formal/gen_goal_slides_l12.py
col = {"in":   ("#f6efdf", "#a8781f"),   # 자료(예시) — 이 색은 자료 전용(R2)
       "rule": ("#e6f1e8", "#3f7a52"),   # 규칙 판정 계열 과업
       "cert": ("#e5ebf5", "#3f5f8f"),   # 인증·누적·표시·재검증 계열 과업
       "gray": ("#eeeeee", "#8b93a0")}   # 표지 — 「여기 없다」(실행 위치)
BLUE = "#3f5f8f"                          # 구현 **글씨** 전용 — 선의 색 축은 판정이라 선에는 쓰지 않는다
```

선언만 하고 쓰지 않는 색은 두지 않는다(`warn` 삭제, 2026-09-06). 범례가 약속한 색과 실제
사용은 **계수로 대조**한다 — 슬라이드 × 색을 세어 개요와 단계의 불일치를 잡았다(G391).

### (나) 노드 — 네 타입의 코드 표현

```python
IOT = namedtuple("IOT", "given task yields")        # 입력 → 과업 → 출력 (§12.1 #2)

E = lambda *ls:                (list(ls), "in", "ex")          # 자료  — 원형 · 채움 · 호박
T = lambda i, t, o, k="rule":  (IOT(i, t, o), k, "task")       # 과업(L0) — 직사각 · 투명(실선 테두리)
B = lambda i, t, o, k="rule", p=None: (IOT(i, t, o), k, p)     # 과업(L1) — 부모는 L0 과업
#   구현: l2 원소의 첫 칸(코드 이름) — 파란 글씨로 나타난다
#   표지: 타입이 아니다 — kind="gray" 또는 빈 칸 또는 강조로 **다른 노드에 붙는다**
```

**자료는 `IOT` 를 갖지 않는다** — 값 자체가 내용이라 입력·출력 레지스터가 없다. 이것이
코드에서 자료와 과업을 가르는 실제 차이이고, 모양(원형/직사각)은 그 차이의 표현이지 원인이 아니다.

### (다) 관계 — 세 종류의 코드 표현

```python
# 1. 예시 흐름 — 한쪽 끝이 자료이면 예시 간선이다 (R5)

#    실선 · 곡선(Q) · 화살표

# 2. 파이프라인 흐름 — 같은 층의 과업 사이 (R4: edges1 은 L1 행 안에서만 정의된다)
seq = lambda n: [(i, i + 1, "") for i in range(n - 1)]
#    stroke-dasharray "6 4" · 직선(L) · 화살표

# 3. 구체화 = 전체/부분 — 과업 → 그 핵심 구성. **화살촉 없음**(배치가 방향) — C4 존재 관계
```

`l2` 원소가 구체화의 아래쪽 끝을 선언한다 — 1:1 이면 `(부모, 코드, 무엇을 하는가)`,
1:N 이면 `(부모, 코드, 구성 과업 이름, 한 마디)`. **원소 수가 상자 모양을 정한다**(합친 상자냐
갈라진 구성이냐)이지 사람이 그때그때 고르지 않는다.

### (라) 규칙 — 단언의 실제 문장

```python
assert kind != "in" or role == "ex"        # R2 호박은 자료 전용
assert all(iot)                            # R7 IOT 삼항에 빈 칸 없음
assert p in tasks0                         # R1 구체화의 위쪽 끝은 과업(자료는 구체화되지 않는다)
assert wid(line) <= bw - 8                 # R6 상자 폭(한글 10.5px · ASCII 5.9px)
assert len(fanned) <= 1                    # 한 단계에 갈라지는 과업은 하나까지(자리 계산)
```

R3·R4 에는 단언이 **없다**. 위반을 표현할 수 없는 자료 구조라 단언이 항상 참이 되고, 그런
가드는 정상 가드와 관측값이 같아 아무것도 막지 못한다(이 저장소의 `assert_5` 선례).

### (마) 음성 확인 — 규칙이 살아 있음을 매번 다시 잰다

각 단언마다 위반을 하나 넣어 보고 **생성이 실패하는지** 본다. 2026-09-06 실측 전부 발동:

| 넣은 위반 | 나온 것 |
|---|---|
| `B("원문", "문장 분리", "")` | `AssertionError: IOT 삼항에 빈 칸이 있다` |
| `B("절", "격 골격", "주어·술어·격", "in")` | `AssertionError: 호박은 예시 전용이다` |
| 부모를 자료 id 로 (`..., "rule", "c"`) | `AssertionError: 구체화의 위쪽 끝이 작업 노드가 아니다` |

## 7. 이 체계가 답하지 못하는 것

- **노드의 동일성**. 같은 작업이 두 그림에 나오면 같은 노드인가? 지금은 이름이 같으면
  같다고 읽지만 강제하는 것이 없다 — 이름을 고치면 조용히 다른 노드가 된다.
- **구체화의 완전성**. 「핵심 구성 N」이 정말 그 작업의 전부인지 그림은 말하지 않는다.
  6단계 재검증의 구성 셋은 코드의 순서 계약에서 왔지만(§`_assert_certificate_grants_verdicts`),
  다른 곳은 사람이 골랐다.
- **자료의 출처**. 자료 노드의 값이 실측인지 예시인지 구별하는 표시가 없다. 지금은
  캡션·주석이 말한다.
