# Common — 모든 관계 유형에 적용되는 Default

## 목차

1. 순위경쟁과 공통 표현 규칙
2. IR 작성
3. 검증·렌더·이미지 READ
4. Main node 9개 초과 시 정보량 조정
5. 명시되지 않은 유형과 보류

모양이 무엇을 뜻하는지는 유형마다 다르다. **이 파일은 모양의 의미를 정하지 않는다.** 의미는 각 [relation_types/](relation_types/) 파일을 따른다.

## 1. 순위경쟁과 공통 표현 규칙

**순위경쟁**: 한 도식에 여러 유형이 있어 같은 모양이 두 의미로 읽힐 수 있으면, 아래 사용빈도 순으로 앞선 유형의 의미를 기본으로 두고 뒤 유형은 다른 축으로 구분한다.

```
execution_flow > execution_flow 안의 whole_part > goal_means > is_a
```

- 구분에는 채움(fill)과 색을 쓰고, 그 뜻을 반드시 Legend에 적는다. Legend 없이 fill·색에 의미를 싣지 않는다.
- 같은 도식 안에서 한 표현은 한 의미로만 읽혀야 한다. 같은 기호는 같은 종류에만 쓴다.

**표현 축의 식별력 순위** (높을수록 먼저, 중요한 구분에 쓴다):

```
화살촉 유무 > rect/stadium > 점선/실선 > 채움 > 색(5색) > 모서리 각 > 곡선/직선
```

- **색**: 흑·백·빨·초·파 5색만 쓴다.
- **점선**: 간격 = 확실성. 간격이 넓을수록 불확실하다. edge는 긴 대시, 영역은 짧은 점이다.
- **곡선**: node가 상하좌우로 정렬돼 직선이 자연스러우면 쓰지 않는다. 다른 요소를 우회해야 할 때만 쓴다.
- **Legend**: 그 도식에 실제로 나온 종류만 싣는다.
- **대조와 식별**이 이 체계의 상위 원칙이다. 규칙을 지켜도 렌더 결과에서 대조가 떨어지면 고친다.

## 2. IR 작성

```json
{
  "w": 780, "h": 160,
  "legend": {"verify": {"color": "green", "label": "검증하는 Task"}},
  "nodes": [
    {"id": "src", "role": "entity", "label": "원문", "x": 90, "y": 80},
    {"id": "grp", "role": "process", "label": "검증 묶음", "x": 330, "y": 80, "expandAt": 0, "drawRegion": true, "source": "request"},
    {"id": "chk", "parent": "grp", "role": "process", "kind": "verify", "label": "대조", "x": 330, "y": 80}
  ],
  "edges": [{"from": "src", "to": "chk", "meaning": "execution_flow", "certainty": "solid"}]
}
```

- **node**
  - `role`: 모양을 정한다(`process` = rect, `entity` = stadium). 유형 파일이 정한 뜻대로 고른다.
  - `x`, `y`: 중심 좌표. `w`, `h`로 크기를 바꿀 수 있다(기본 176 × 44). `w`를 주지 않으면 라벨 길이에 맞춰 넓어진다. `w`를 준 경우 라벨이 넘치면 `VB-LABEL-FIT` 경고.
  - `kind`: 종류. 색은 `legend`에 정의한다.
  - `parent`: 이 node를 품는 전체 node의 id.
- **전체(group) node**
  - `x`, `y`: 접혔을 때의 위치. 접힐 수 있는 전체 node에는 반드시 준다(없으면 부분 node들의 중심에 자동 배치하고 `VB-GROUP-POS` 경고).
  - `expandAt`: 이 L 단계부터 펼쳐진다. 그보다 낮은 단계에서는 접혀 [+]가 붙는다. 접혀도 자기 `role`의 모양을 유지한다.
  - `drawRegion: true`: 펼쳤을 때 영역을 그린다.
  - `"certainty": "dashed"`: 묶음이 미정이면 준다. 영역이 짧은 점으로 그려진다.
  - `source`: 묶음의 출처. `"request"`(요청에 명시), `"human"`(Human이 고름). 둘이 아니면 `VB-GROUP-SOURCE` 경고
- **edge**
  - `meaning`: 관계 유형.
  - `certainty`: `solid`, `dashed`, 또는 간격 숫자.
  - `arrow: false`: 화살촉을 없앤다.
  - `label`: edge 이름.
  - `from`·`to`는 그 단계에서 **보이는 node**여야 한다. 펼친 전체 node(영역)는 끝점이 될 수 없다. 영역 안의 부분 node를 가리킨다(`VB-EDGE-ENDPOINT`).
  - `loop: true`: 되먹임(cycle). 강조 범위 계산에서 뺀다.
  - `sdx`, `tdx`: 출발점·도착점의 가로 이동.
  - `route`
    - `"hvh"` + `busX`: 여러 입력이 한 node로 모일 때(fan-in) 쓴다. 가로로 나와 `busX`에서 세로로 모인 뒤 가로로 들어간다. 여러 node가 세로로 쌓여 한 곳으로 모이면 기본 경로 대신 이것을 써서, 선이 형제 node를 관통하지 않게 한다.
    - `"curve"`: 우회가 필요할 때만 쓴다.

## 3. 검증·렌더·이미지 READ

```
node scripts/check_ir.mjs diagram.json [--level N] [--expand id,id] [--collapse id,id] [--focus nodeId]
node scripts/render_svg.mjs diagram.json out.svg [--level N] [--expand id,id] [--collapse id,id] [--pad N] [--focus nodeId]
```

- **`check_ir.mjs` 출력**: 규칙마다 PASS/WARN/FAIL을 찍는다. 종료 코드 0 = 통과(경고 허용), 1 = 규칙 위반, 2 = 입력 오류.
- **`RESULT pass`와 종료 코드 0은 완료가 아니다.** WARN은 다음 할 일을 알려 주는 신호다. 특히 `VB-MAIN-COUNT` WARN이 있으면 §4를 끝내기 전에는 완료하지 않는다. WARN을 "의도된 구성"으로 해석해 넘기지 않는다. 넘기고 싶으면 Human에게 묻는다(선택지에 보류 포함).
- **FAIL이면** IR을 고쳐 다시 실행한다. 스크립트가 FAIL이 아니라 **오류로 멈추면**(예: `TypeError`) 먼저 [issue/script_defects.md](issue/script_defects.md)를 읽는다. 서로 다른 의미가 같은 모양으로 그려지는 **동일성 충돌**은 이 단계에서 잡는다.
- **`--level N`**: 추상화 단계 L0–L2로 본다. Z0–Z2와 같은 뜻이다.
- **`--expand`/`--collapse`**: 특정 전체 node만 펼치거나 접는다. 그룹을 하나씩 펼치는 화면을 만들 때 쓴다.
- **여백**: `render_svg.mjs`는 그려진 모든 요소(node, 영역과 라벨, edge 경로, edge 라벨)의 경계 상자를 구하고, 네 방향에 같은 여백(`--pad`, 기본 24)을 더해 캔버스로 삼는다(Graphviz의 bb + pad 방식). 다른 렌더러나 직접 만든 HTML에서도 같은 원리로 상하좌우 여백을 확보한다. `VB-BOUNDS` 경고는 IR의 `w`×`h` 밖으로 나간 node를 알려 준다.
- **이미지 READ는 건너뛸 수 없는 단계다.** 렌더한 결과를 **이미지로 직접 보고** 식별과 대조가 유지되는지 판정한다. 파일을 만들었다는 사실이나 SVG 코드를 읽은 것은 이미지 READ가 아니다.
  - SVG를 이미지로 볼 수 없으면 PNG로 변환해서 본다. 쓸 수 있는 변환 수단을 차례로 시도한다: cairosvg, rsvg-convert, ImageMagick, Inkscape, 헤드리스 브라우저 캡처.
  - 변환 수단이 하나도 없으면 이미지 READ를 **보류**로 notes와 최종 답에 적는다: 무엇을 시도했고 왜 실패했는지. 말없이 건너뛰지 않는다.
- **판정 기준**: 상하좌우 어느 쪽이든 잘리거나 여백 없이 가장자리에 붙거나, 선이 node를 관통하거나, 모양이 뜻과 다르면 IR로 돌아간다. IR을 고쳐도 해결되지 않으면 [issue/script_defects.md](issue/script_defects.md)를 따른다.

## 4. Main node 9개 초과 시 정보량 조정

- **기준**: Main으로 보이는 node는 기본 9개 이하다. `check_ir.mjs`가 `VB-MAIN-COUNT` WARN을 내면 아래를 **순서대로** 시도한다. 배경 처리된 node는 세지 않는다.

**1) 접기.** 요청에 **명시된** 전체–부분 관계가 있을 때만 접는다.
- 요청에 없는 묶음을 만들지 않는다. 이름의 공통 접미어나 비슷함으로 묶는 것도 "묶음 기준을 고르는 일"이므로 접기가 아니라 3) 분할로 다룬다.
- 접은 뒤 다시 `check_ir.mjs`로 Main 수를 센다.
- **IR을 한 번이라도 고치면** 검사·렌더·이미지 READ를 마지막 IR로 다시 한다. 마지막 IR로 만든 산출물만 낸다.

**2) 강조.** 접을 수 없으면 모든 node를 두고, 한 흐름과 그 흐름에 속한 Process의 **공동 입력**(다른 입력)을 Main으로 남긴 채 나머지를 배경으로 약화한다.
- 강조 효과는 반드시 `--focus`로 측정한다. **강조를 쓸지 말지는 `FOCUS 판정` 줄로만 정한다.** 측정하지 않고 강조를 쓰거나 버리지 않는다.
- 흐름이 여러 갈래면 흐름마다 하나씩, **여러 흐름의 공통 시작점이 아닌 흐름 안의 node**로 측정한다.

```
node scripts/check_ir.mjs diagram.json --focus <강조할 node id>
```

- `FOCUS 판정: 강조 무효`(흐려지는 node가 없음) 또는 `강조 후에도 Main 9개 초과`가 나오면 강조로는 해결되지 않는다 → 3)으로 간다.
- 요청이 **HTML이면 정적 출력이 아니다.** 강조가 유효하면 hover로 낸다. HTML에서는 `scripts/dds.js`의 `DDS.render`로 그리고 `DDS.attachHover`로 hover를 연결할 수 있다.
- 정적 출력(이미지·인쇄·PDF처럼 hover·애니메이션·화면 전환을 쓸 수 없는 출력)은 강조할 흐름 후보 2~3개를 Human에게 제시해 하나를 고르게 하고, 그 흐름을 강조한 한 장으로 낸다(`render_svg.mjs … --focus <node id>`). Human이 더 요청하면 흐름별 여러 장으로 낸다.

**3) 분할.** 묶음·분할 기준 후보 2~3개를 Human에게 제시해 고르게 한다(예: 내부/외부, 실시간/배치).
- 선택지에 "보류"를 넣는다. 위임 선택지는 §5의 조건을 만족할 때만 추가한다.
- **Human이 고르기 전에는 최종 도식을 확정하지 않는다.** 기계적으로 나누지 않는다.

## 5. 명시되지 않은 유형과 보류

**경우 2 (명시되지 않은 유형)**
- 요청의 **의미**가 모호하면 그리기 전에 Human에게 묻는다. 무엇을 기준으로, 몇 개로, 어떤 데이터로 그리는지 등을 확인한다.
- 의미는 분명하지만 이 skill에 **표현 방식**이 없으면, 다른 Agent Skill, Tool, GitHub repo를 탐색해 표현 방식을 찾는다. 찾은 방식과 출처를 notes에 적는다.
- 네 유형 중 하나로 억지로 끼워 넣지 않는다.
- **데이터로 그룹을 나누는 요청(군집화 등)**: 분석은 이 skill이 다루지 않는다. 분석 방법도 이 skill이 정하지 않는다. 다른 Skill·Tool로 **분석을 먼저 끝낸 뒤**, 그 결과를 도식으로 그릴 때 이 skill을 쓴다.
  - 순서: 그룹 개수를 먼저 묻고 → 분석하고 → 그 결과를 보고 그룹 이름을 추천한다.
  - 그룹 개수는 Human이 정한다. 개수 질문의 선택지는 숫자와 보류만 둔다(예: `3개` / `4개` / `보류`). 그룹 이름·특성은 분석 전에는 선택지에도 설명에도 쓰지 않는다.
  - 나뉜 근거는 데이터 시각화로 보인다. **관계 도식만 내고 끝내지 않는다.** 데이터 시각화 파일을 따로 만든다.
  - 그룹 번호(인코딩 값)와 설명 이름은 서로 다른 계층의 label임을 밝힌다.
  - 결과를 관계 도식으로도 그리면, 데이터를 보고 나눈 것이므로 whole_part로 그리고 데이터 시각화와 함께 낸다.

**경우 3 (애매하거나 판단할 수 없음)**
- Human에게 폐쇄형 질문을 하고, 선택지에 **"보류"**를 넣는다.
- 선택지는 기본 경로일 뿐이다. Human이 선택지 밖에서 답하면 그 답을 따른다.

**Human이 보류하면 (Agent의 책임)**
- 보류를 줄이는 것은 Agent의 몫이다. 다음 중 하나로 진행한다.
  - 결정을 돕는 설명(이해를 돕는 풀이, 장단점)을 더하고 다시 묻는다.
  - 위임 조건을 만족하면 Agent가 결정한다.
- **위임 조건**: 꼭 필요할 때만, 그리고 검증 결과와 근거가 분명할 때만. 위임을 선택지로 줄 때는 값과 근거를 함께 적는다(예: "추천값 3개로 진행 — 근거: 3개에서 오차 감소가 가장 크게 꺾임"). 값을 아직 계산하지 않았으면 위임 선택지를 넣지 않는다.
- 보류가 풀리지 않으면 그 부분은 그리지 않고 나머지만 산출하며, 미결로 기록한다. Human이 요청하면 도식에는 표시하지 않고, 도식 밖에 무엇을 왜 그리지 않았는지 글로 적는다.
- "판단불가"는 선택지로 쓰지 않는다. 판단하기 어려운 상황은 위 방법으로 해소할 대상이다.

**기록에는 결정 주체를 적는다**

```
결정: Human — 3개
결정: Agent(위임) — 3개. 근거: …  검증: …
보류: 그룹 개수 — 다음 행동: 장단점 정리 후 재요청
```
