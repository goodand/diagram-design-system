> 이 파일은 Default가 아닌 세부 규칙과, 규칙을 수정할 때 보는 전체 규칙이다. 괄호 안의 ARG·DEC·R 번호는 Web에서 관리하는 결정 기록의 근거 ID다. 현재 적용할 표현 규칙을 이 Skill 안에 유지하며, 원장·변경 이력은 복제하지 않는다.

## 1. 설계 원리

- **표현(Expression)**: 유한하고 식별 가능한 시각 형태(edge(Link), node(Vertex), 화살촉, 점선 등)
- **의미(Meaning)**: 키워드를 의미의 대리자(proxy)로 사용
- **매핑(Mapping)**: 표현 ↔ 의미를 1:1 또는 1:N으로 대응, 우선순위 존재
- **언어로서의 design system**: 형태 → 해석 → 의사소통

> 표현·의미·매핑의 분리 자체가 이 체계의 상위 구조다. (ARG-056)

**해석 우선순위**: 사용자의 현재 프롬프트 > design system 규칙 > 예시 HTML 시각 구현 (ARG-057)

### 의미 우선과 실행순서

- **의미가 표현보다 중요하다.** 다만 복잡도 관리를 위해 표현(Lexical) 층을 실행순서상 먼저 고정할 수 있다. (ARG-044, DEC-001)
- **우선순위와 실행순서는 다를 수 있다.** 의존성·인과·복잡도·기존 체계 때문에 우선순위가 낮은 작업을 먼저 할 수 있다. (ARG-043)
- 초기에 무엇을 고정하고 무엇을 결정하는지가 이후 구조를 크게 좌우하므로, 고정한 것은 명시적으로 기록한다. (ARG-041)
- 외부 체계의 한계로 표현을 바꿔야 할 때, **의미가 크게 변하지 않으면** 표현 변형을 허용한다. 판정 기준은 §13.4에 둔다. (DEC-001, ARG-065)

### 표현 증식 규칙

- Human의 Wants는 표현을 증식시킬 수 있다. 증식된 표현은 **모호성을 줄이고 단일 의미 해석을 유도할 때만** 채택한다. (ARG-029)
- 매핑이 체계 수준에서 1:N이더라도, **같은 diagram 안에서는** 한 표현이 한 의미로만 읽혀야 한다. 같은 기호는 같은 종류를 나타낸다. (ARG-029, ARG-018)

### 효과 우선과 정보량 관리

- 기능 수보다 시각화의 **효과와 목적**에 집중한다. (ARG-007)
- 목표 효과에 필수적인 구성요소만으로 작동시킨다. (ARG-039)
- 한 번에 제시하는 정보량을 관리한다. 과한 정보는 이해 부담을 키운다. (ARG-047)
- Main으로 표현하는 node는 기본 **9개 이하**로 한다. 초과 시 처리는 §7에 둔다. (DEC-025)

### 대조와 식별 우선

- 대조와 식별이 잘 되는 것을 이 체계의 상위 원칙으로 둔다. 표현을 고를 때와 외부 도구의 변형을 판정할 때 모두 이 기준을 쓴다. (DEC-008, §13.4)

### 고정의 의미

- 표현을 먼저 고정하는 목적은 수정할 때 전체를 일관되고 예측 가능하게 바꾸기 위해서다. 고정은 불변이 아니라 **변경의 기준선**이다. (DEC-013, DEC-001 보완)

## 2. 표현 위계

### 위계 기준

- **표현 위계**: 식별력(identifiability) 중심으로 결정 (ARG-058)
- **의미 위계**: 사용빈도 중심으로 결정 (ARG-059)

### Core/Main/Sub 명칭에 대한 문제 제기

> Core/Main/Sub 명칭을 없애고, 결정된 우선순위를 모두 명시적으로 표현하는 것도 방법이다.

### 표현 식별력 우선순위

```
Arrowhead 유무 > rect/stadium > dashed/solid > fill > color(5색) > corner rounding > 곡선/직선
```

> 점선/실선은 식별력으로는 Core급이나, 점선 간격이 너무 좁으면 시각적 가독성이 낮아 2순위로 배치되었을 뿐이다.

### 현행 표현 축 정리

| 우선순위 | edge(Link) | node(Vertex) |
|----------|----------|-------------|
| 1 (최고 식별력) | Arrowhead 유무 | 직사각형 / Stadium |
| 2 | 점선/실선 (certainty 축) | 채움(fill) 유무 |
| 3 | 색상 — 흑/백/빨/초/파 5색 (식별 용도, 심미적·Art 영역에서도 사용 가능) | 색상 — 흑/백/빨/초/파 5색 |
| 4 | 곡선/직선 (식별성은 존재하나 시각적 안정성 낮음, 직선 자연 시 곡선 지양) | 모서리 각 — 둥근/뾰족 |

> v2 정정: v1 표의 node 열은 모서리 각(3)·색상(4) 순이었으나 전체 순서 `fill > color > corner rounding`(ARG-058)과 충돌하여 색상(3)·모서리 각(4)으로 맞췄다. 그 결과 색상은 edge·node 양쪽 모두 3순위다.

### 곡선에 대한 결정

- 곡선은 식별성 자체는 존재하나 **시각적 안정성이 낮음** (layout 변경 시 형태 변화)
- **노드가 상하좌우로 정렬되어 직선이 자연스러운 경우, 의미적·장식적 목적으로 곡선을 사용하는 것을 지양함**
- **레이아웃상 다른 요소를 우회해야 하는 등 곡선이 필요한 경우는 허용**
- 식별력 4순위로 배치 (ARG-061)

## 3. 의미 위계

### 위계 기준: 사용빈도

```
execution_flow > execution_flow_whole_part > goal_means > is_a
```

| 사용빈도 순위 | 의미 | 설명 |
|--------------|------|------|
| 1 | **execution_flow** (실행흐름) | Process / Entity 구분. 가장 기본적 관계 |
| 2 | **execution_flow 내 whole_part** | 실행흐름 안에서 whole/part가 메타 수식어로 작동 |
| 3 | **goal_means** (목적/수단) | 수단→목적, N:1 또는 N:N |
| 4 | **is_a** (분류) | 상위개념/하위개념 chain |

### execution_flow 상세: Process와 Entity

- **Process**: Task, Action, AtoB, Module, Pipeline, Function 등의 표현으로 사용될 수 있음. **rect(직사각형)로 표현한다**
- **Entity**: 어떠한 data, interaction, action, relation을 input/output으로 사용하여 Process의 전/후에 있는 것으로 표현. 일종의 객체라고 표현할 수 있음. **stadium으로 표현한다**
- **실제 사용**: 사용자의 직관성·비개발자 이해 용이성 때문에 Process에서는 **Task**로 사용하는 것이 일반적. Task를 구체적으로 표현하려는 의도에서 **Action**으로 표현하기도 함

#### Process / Entity 식별 표기

| 역할 | node 표현 | 비고 |
|------|-----------|------|
| **Process** | rect (직사각형) | Task / Action 등으로 명명 |
| **Entity** | stadium | Process의 input/output으로 전·후에 위치 |

> 두 역할은 표현 위계 1순위 축(rect/stadium)으로 갈린다. 따라서 execution_flow 안에서 Process와 Entity의 구분은 색상이나 채움 같은 하위 축을 쓰지 않고 node 형태만으로 식별된다. (ARG-060)
>
> Entity를 생략하고 Process만 이어 붙이면 rect 단독 구성이 되며, 이때도 의미는 execution_flow로 유지된다.

#### Task 종류 구분

- Task가 **하는 일의 종류**(예: 생성·검증·결정)를 구분해야 하면 rect/stadium 축은 건드리지 않고 하위 축(주로 색상)으로 구분하고 Legend로 설명한다. (ARG-018, ARG-025)
- 의미적 Hierarchy를 먼저 세운 뒤 종류를 나누며, 색·기호는 맥락상 필요할 때만 제한적으로 쓴다. (ARG-018)

## 4. 네 가지 의미의 특성 비교

| 특성 | execution_flow | goal_means | whole_part | is_a |
|------|---------------|------------|------------|------|
| 기본 그래프 | DAG + cycles 허용 | DAG | tree (기본) | tree (기본) |
| certainty 적용 | ✓ | ✓ | ✓ (묶음 미정만, 정도 없음, DEC-007) | ✗ |
| 메타 수식 관계 | whole_part, certainty가 내부에서 수식어로 작동 | certainty가 수식어로 작동 | — | — |
| 상대적 chain | — | 수단→목적 | 부분 → 전체 (X는 Y의 부분) | 상위↔하위 |
| 추상화와의 관계 | — | — | **높은 관련성** (추상화 ≈ 상단 유지, 하단 은닉) | 단어 의미 이해를 위한 chain |

### 의미 간 관계에 대한 관찰

1. **whole/part는 추상화와 직결**: graph 추상화 = tree 상단 유지 + 하단 은닉. whole/part 자체가 이 구조.
2. **whole/part는 execution_flow 안에서도 사용됨**: 메타 수준 수식어로 작동
3. **certainty는 is_a에 적용되지 않음**: is_a는 분류 체계이므로 확실/불확실 축이 부적합. 이 결정은 v3에서도 유지한다. 분류가 여러 가지로 가능하거나 label이 정해지지 않은 경우는 이 체계의 표현 대상이 아니다. (DEC-009, DEC-023)
4. **is_a와 whole_part의 tree 예외**:
   - 두 개 이상에서 상속 (다중 상속) → DAG
   - 부분은 같은데 전체가 다른 경우 존재
   - 같은 전체에서 다른 부분 → 이 경우 추상화를 많이 사용
5. **is_a의 용도**: 명제·문장·문단에서 특정 단어의 의미를 이해하기 위해 상위/하위개념 chain으로 표현하거나, 단어들 간의 관계를 표현
6. **is_a와 whole_part의 경계**: is_a는 정의의 다른 표현(유개념 + 종차)이며 정의가 먼저다. 데이터를 보고 해석해 나눈 뒤 이름을 붙였다면 whole_part다. whole_part는 "X는 Y의 부분"으로 읽으며 포함이나 집합 기호로 읽지 않는다. 부분끼리 겹치는 것은 흔하다. 셀 수 있음은 whole_part의 근거가 될 수 있고, 세는 대상은 구성원(index·인코딩 값)이며 부분의 이름은 설명 label이다. (DEC-044, DEC-045, DEC-046, DEC-048)

## 5. 표현 ↔ 의미 매핑 (Version B)

> Version A(곡선 사용)는 참고용으로 보존하나, 이 세션에서는 **Version B**를 선택.

| 노드 조합 | 의미 |
|-----------|------|
| rect → rect | goal_means |
| stadium chain | is_a |
| rect 단독 또는 rect+stadium 혼합 | execution_flow — rect = Process, stadium = Entity |
| 포함 영역(region) | whole_part |

### execution_flow와 goal_means 겹침 해결

> 둘 다 rect + arrowhead이지만, **위계를 따라서 맥락에 따라 사용**한다.
> 같이 쓰이는 경우 **채움(fill) 유무, 색상**으로 충분히 표현 가능.
> 이때 fill·색상이 무엇을 뜻하는지 Legend에 명시한다. Legend 없이 fill·색상에 의미를 싣지 않는다. (ARG-018, ARG-025, ARG-029)

## 6. 확실성 축 (Certainty — 의미 매핑과 직교)

| 상태 | 표현 |
|------|------|
| 확정/존재 | 실선 (solid) |
| 불확실/미정 | 점선 (dashed) |
| 확실성 정도 | dash-gap gradient (좁은 간격=확실에 가까움, 넓은 간격=불확실) |

적용 범위: execution_flow ✓, goal_means ✓, whole_part ✓, is_a ✗ (ARG-062, DEC-007)

### 정의

- 확실성 축은 관계가 **확정되었는가**를 넓게 뜻한다. 여러 표현과 여러 의미를 허용하고, Agent가 맥락으로 판단하되 공존하거나 순위가 경쟁하면 정책(§5 겹침 해결)을 따른다. 1차 적용 맥락은 사용빈도상 execution_flow이며, 사용자 interaction도 여기에 포함될 수 있다. (DEC-006)
- 내용 미정의 주체는 원천이다. execution_flow·goal_means의 edge와 whole_part 영역 모두 Human 미검토나 Agent 자신의 불확실을 점선으로 바꾸지 않는다(DEC-141).
- **간격 = 확실성**은 edge와 영역 모두에서 같은 뜻이다. 대시 길이는 요소 종류를 가른다(edge = 긴 대시, 영역 = 짧은 점). (DEC-007)

### whole_part 영역

| 상태 | 영역 경계 |
|------|-----------|
| 묶음 결정 | 실선 |
| 묶음 미정 | 짧은 점 `2 6` (간격 6 = edge 점선과 같은 "미정") |

- 접힌 전체 node에는 내용 미정을 나타내는 별도 점선 테두리를 만들지 않는다. 영역의 짧은 점은 펼쳤을 때 표현한다(DEC-099).
- 묶음 미정에는 정도를 두지 않는다. 영역의 간격은 `2 6` 하나만 쓴다. (DEC-007)
- 여기서 내용 미정은 원천이 미정이라고 표현한 것을 뜻한다. Agent가 정한 묶음도 실선이며, Human 미검토나 Agent 자신의 불확실은 점선의 이유가 아니다. 검토 대기는 REVIEW 글로 알린다. (DEC-133·134·141)
- 그리기 형식은 원천 존재 유무에 따라 바꾸지 않는다. 원천과 그림의 점선 유무를 기록하는 외부 판정과, 이 Skill의 의미 정합 평가는 구분한다. (DEC-138·146·147)

## 7. 추상화 단계

- **L0** (가장 추상) → **L10** (가장 구체)
- 일반적 출력: L0–L2 (ARG-063)
- Z0–Z2와 L0–L2는 기호만 다르고 같은 의미다(Zn ≡ Ln). 한 문서·도식 안에서는 한 표기를 일관되게 쓰되, 둘을 하나로 통일하지는 않는다. (DEC-012)
- 다음 단계 생성 전 반드시 검증 필요 (코드/문서 대조) (ARG-063)
- 검증은 코드/문서 대조에 더해, **렌더된 Image를 AI가 READ하여** 실제 시각 결과까지 확인하는 루프를 지향한다. (DEC-003)
- 일반 출력을 L0–L2로 제한하는 것은 범위를 줄여 검증 비용·복잡도를 낮추고 좋은 것에 집중하는 방향과 같다. (ARG-006, ARG-039)

### 같은 소스의 단계별 재렌더링

- 추상화 단계는 **하나의 소스**(IR 또는 mmd)에서 detail level만 바꿔 다시 그린다. 단계마다 도식을 따로 새로 그리지 않는다. (ARG-065)
- 상위 단계는 whole_part tree의 하단을 접어 만든다. 접힌 node로 향하던 edge는 가장 가까운 보이는 상위(전체) node로 올리고, 중복·자기 edge는 지운다. (§4 관찰 1, v2 구현 규칙)
- L 단계는 **의미**(whole_part tree를 어디까지 접는가)로 정의한다. 외부 렌더러 diagram-design의 detail 단계와는 대응표로만 연결한다: L2 ↔ faithful, L1 ↔ balanced, L0 ↔ simplified. 도구 쪽 node 수는 도구의 파라미터이며 L 정의를 바꾸지 않는다. (DEC-014, ARG-065, ARG-067)

### Main node 수와 정보량 조정

- Main으로 표현하는 node는 기본 **9개 이하**다(L0·L1·L2 공통). 배경 처리된 node는 세지 않는다. 이 값은 금지가 아닌 **경고 기준**이며, 변경의 기준선으로서 바뀔 수 있다. 단계 간 비율은 고정하지 않는다. (DEC-025, DEC-014)
- 9개를 넘으면 다음 순서로 조정한다. (DEC-026, DEC-015를 수정)

| 단계 | 수단 | 조건 | 동작 |
|------|------|------|------|
| 1 | 묶음과 접기 | 요청의 전체–부분 또는 Agent가 표현을 위해 정한 묶음 | 전체 node로 접고 [+]로 펼칠 수 있게 두며, 나머지는 다른 L에서 보여준다. Agent가 정한 묶음은 먼저 그리고 기준·소속을 사후 검토받는다. 요청 사실이나 Human 결정으로 가장하지 않는다 (DEC-132·133·143) |
| 2 | hover 강조 | 접을 수 없음 (같은 위계의 형제가 많음) | 모든 node를 두되 관련 흐름과 그 공동 입력만 Main으로 강조한다 (§10.2, DEC-029) |
| 3 | 분할 | 강조 후에도 Main이 9개 초과, 또는 강조해도 흐려지는 node가 없음(강조 무효, R9) | 분할안 2~3개를 Human에게 제시해 고르게 한다(보류 포함). 기계적으로 나누지 않는다 (DEC-016) |

- 정적 출력에서 hover를 쓸 수 없을 때는 §11.6을 따른다.
- 강조의 효과는 검증 도구의 focus 측정(강조 후 Main 수, 흐려지는 node 수)으로 판정한다. (R4, R9)
- 접힌 전체 node는 자기 역할의 모양을 유지한다. 그룹은 하나씩 펼칠 수 있어야 한다. 접힌 node의 라벨은 [+]와 겹치지 않게 둔다. (R2, R8, R13)
- 도식은 상하좌우 여백을 보존한다. 그려진 모든 요소의 경계 상자에 네 방향 같은 pad를 더한다(Graphviz의 bb + pad 방식 재사용). 접힐 수 있는 전체 node에는 좌표를 준다. (DEC-042, R10, R11)

### 추상화에서의 그래프 처리

- tree의 상단을 남기고 하단을 은닉하는 방식
- tree가 아닌 것을 tree로 가정하여 tree 방식으로 사용하는 경우도 존재
- 정보 손실 유형:
  - **구조적 손실**: N:N → 1:N tree로 변환 시
  - **의미적 손실**: 세부사항 생략/캡슐화

## 9. UX 분석

### 식별 용이성 순위

```
Arrowhead > rect/stadium > dashed/solid > fill > color(5색) > corner rounding > 곡선/직선
```

> v2: §2의 식별력 순서(ARG-058)와 항목 수를 맞추기 위해 곡선/직선을 끝에 추가했다.

### 시각 안정성

- 곡선: 식별성은 있으나 **시각적 불안정** → 직선 자연 시 곡선 지양, 라우팅 필요 시 허용

### 그림 편의성

**node(Vertex)**: 직사각형 > 선 > 원 > 색상 변경 옵션 > 각 둥근 직사각형 > Stadium

> 4순위는 칠하는 행위가 아니라 **색상 변경 옵션**의 유무를 뜻한다. 색을 바꿀 수 없으면 채움 유무 자체를 표현할 수 없으므로, 채움(fill) 축이 성립하기 위한 선행 조건이다.

**edge(Link)**: 점선 > 화살표

### 그래프 표현 수준

**위상 복잡도**: tree → DAG → DAG with cycles

**Edge 복잡도**: 단일 type → 2–3 types → edge에 설명 필요

**상대적 chain**:

| 의미 | chain 방향 |
|------|-----------|
| whole/part | 부분 → 전체 (X는 Y의 부분) |
| goal/means | 수단 → 목적 |
| is_a | 상위개념 ↔ 하위개념 |

## 10. 보조 표현: Legend, hover, 애니메이션

> 이 절의 표현은 §2 식별력 위계에 새 축을 추가하지 않는다. 정적 도식의 의미를 보조하며, 불필요하면 쓰지 않는다.

### 10.1 Legend

- 색상, 특정 색 박스, 기호가 무엇을 뜻하는지 Legend로 설명한다. (ARG-025)
- 의미적 Hierarchy를 먼저 세우고, 같은 기호는 같은 종류에만 쓴다. (ARG-018)
- Legend에는 그 diagram에 **실제로 등장한 종류만** 싣는다. Legend로 도식에 없는 요소를 보충하지 않는다. (archify의 legend auto 규약을 차용, ARG-066)

### 10.2 hover 강조

- hover 시 관련 flow를 강조하고 나머지는 배경처럼 약화한다. (ARG-023)
- 강조 범위는 국소 연결이 아니라 **Input에서 Output까지 이어지는 관련 흐름 전체**다. (ARG-024)
- 관련 흐름은 독립성·의존성·응집도·결합도를 고려해 고른다. 되먹임(cycle) edge는 강조 범위 계산에서 분리할 수 있다(v2 구현 선택). (ARG-024)
- 강조된 Process의 **다른 입력(공동 입력)**도 Main에 포함한다. 강조가 "이 Process는 이 입력만 받는다"로 오독되지 않게 하기 위함이다. 포함 후 Main이 9개를 넘으면 §7의 다음 단계(분할)로 간다. 정적 출력과 hover에 같이 적용한다. (DEC-029)
- 독립 구조, 재사용 후보, 반복 구조의 비효율을 드러내는 데 활용할 수 있다. 불필요하면 쓰지 않는다. (ARG-024)

### 10.3 애니메이션

- 애니메이션은 구조 해부 Diagram의 **정식 표현 전략**이다. (ARG-010)
- 용도는 **전달/실행 흐름**, 즉 무엇이 어디로 전달되는지 보여주는 것에 한정한다. 불필요하면 쓰지 않는다. (ARG-010)
- 재생은 유한(1회)하게 하고 `prefers-reduced-motion`을 존중한다. 애니메이션 없이 정적 도식만으로 의미가 성립해야 한다. (archify의 finite motion 규약 참고, ARG-022의 Main 우선)

## 11. Mode와 화면 계층

### 11.1 Mode 구성

- **기본 Mode**(구조적 실행흐름), **설명 Mode**(설명 추가), **예시 Mode**(실제 예시)를 분리한다. (ARG-014)
- Task가 "무엇을 하는지"에 대한 서술은 구조가 아니라 **설명 계층**에 둔다. (ARG-017)
- 기본·설명·예시·애니메이션 버튼은 모양·크기·위치를 통일한다. (ARG-015)

### 11.2 Mode의 시각적 계층

- Mode 전환은 Z0–Z2 Stage(구조) 이해를 **보조하는 옵션**이다. 상단에 크게 두어 구조보다 상위 계층처럼 보이게 하지 않는다. (ARG-019, ARG-014)
- 도식 아래, 캡션 곁에 작게 두는 것을 기본으로 한다. (v2 구현 선택)

### 11.3 조작 일관성

- 요소를 클릭했을 때 선택 옵션 수가 예상 없이 바뀌지 않게 한다. (ARG-020)
- 펼치기 affordance로 [+] 아이콘을 쓴다. (ARG-012)
- node의 브라우저 기본 포커스 테두리는 식별에 도움이 되므로 유지한다. 도식에 지정하는 5색 규칙을 이유로 브라우저 기본 동작을 바꾸지 않는다. (DEC-112)

### 11.4 Main과 Side

- Main만으로 Human의 이해를 충분히 달성하는 것을 우선한다. Sub/Side는 차선책이다. (ARG-022)
- Side 예시 이미지·reference는 Golden Case의 기본 전략으로 **쓰지 않는다**. (ARG-022, 미채택)
- 우측 설명 패널은 시선 이동을 요구해 한눈에 보기 어렵다. 보조 자료를 둘 경우 Main과 Side의 경계를 명확히 한다. (ARG-021)

### 11.5 UX writing

- 'shape 표시' 기능은 유지하되 그 명칭은 쓰지 않는다. (ARG-013)
- '간소화'는 설명용 임시 표현이며 확정된 UX 명칭이 아니다. (ARG-016)

### 11.6 정적 출력

- **정적 출력**은 hover, 애니메이션, 화면 전환(Mode 버튼, L 단계 버튼, [+] 펼치기)을 쓸 수 없는 출력이다. 예: 이미지, 인쇄, PDF, 슬라이드 캡처.
- 정적 출력에서 접기가 불가능하면 기본은 **흐름 하나만 강조한 한 장**이다. 복잡도 관리를 위함이다. (DEC-027)
- 강조할 흐름은 Agent가 후보 2~3개를 제시하고 Human이 하나를 고른다. 렌더는 `drd.mjs finalize --focus <node id>`로 한다(R18). Human이 선택지 밖에서 더 요청하면(예: 흐름별 여러 장) 그에 따른다. (DEC-028, DEC-030)
- 강조한 한 장에서도 Main(공동 입력 포함)이 9개를 넘으면 §7의 분할로 간다. (DEC-026, DEC-029)

### 13.1 도입 목적

- 외부 도구의 목적은 예쁜 그림이 아니라 기존 Diagram 규칙의 **준수·재렌더링·검증의 기계화**다. (ARG-064)
- 재사용의 주목적은 생산성보다 **일관성, 신뢰성, 더 뛰어난 기존 산출물의 응용·활용**이다. (DEC-002)
- 현재 설계보다 잘 만든 외부 diagram 사례를 찾아 비교하고 수정에 반영한다. (ARG-026)

### 13.2 archify: Typed JSON IR과 validation gate (구조 차용)

- archify를 그대로 도입하지 않고 **Typed JSON IR과 validation gate 구조**를 현재 의미 체계에 맞게 변형해 자체 규칙 검증기를 만든다. (ARG-066)

- 검증 실패는 규칙 코드, 대상, 근거, 허용 수정안을 담은 receipt로 보고하고, 모든 규칙을 통과한 산출물만 이전 산출물을 대체한다. (archify의 diagnostics·last-good 규약 참고)

### 13.3 diagram-design: 단계별 재렌더러

- diagram-design을 외부 렌더러로 도입한다. 동일 mmd 소스를 detail level별로 다시 그리는 발표·공유용이다. (ARG-065)

### 13.4 규격 보존: 역전 금지

- 외부 도구가 자체 시각 언어를 가져도 Version B 규격을 도구에 맞춰 바꾸지 않는다. (ARG-067)

- **판정 기준**: 축의 순위가 아니라 **렌더 결과의 식별과 대조**로 판정한다. 렌더된 이미지를 READ해 식별·대조가 유지되면 허용하고, 떨어지면 거부한다. 서로 다른 의미가 같은 표현으로 그려지는 **동일성 충돌**은 규칙 기반 검증기로 잡는다. (DEC-011, DEC-008)
- 예: stadium을 둥근 rect로 그림(동일성 충돌, 거부), 저대비 파스텔 색(대조 저하, 거부), 정렬된 배치의 곡선(READ 결과 대조 유지 시 허용).

- Human 만족도가 목적에 포함되면 Artifact를 시각화해 Human이 직접 확인할 수 있게 한다. (ARG-045)

## 16. Agent skill 운용

### 16.1 분류 label 라우팅

- Agent는 skill의 YAML을 READ하고 요청의 **분류 label**부터 판정한다. YAML frontmatter는 Anthropic Skill authoring best practices를 따른다(`name`, `description`). (DEC-019, DEC-020, DEC-021)
- `SKILL.md`는 YAML 다음에 "분류 label이 없을 수 있다"는 경고문을 두고, 세 경우를 명시한다. (DEC-022)

| 경우 | 처리 |
|------|------|
| 명시된 label (execution_flow, goal_means, whole_part, is_a) | 이 문서의 규칙대로 그린다 |
| 명시되지 않은 label | 의미가 모호하면 Human에게 추가 질문·설명을 요청한다. 표현 방식은 다른 Agent Skill, Tool, GitHub repo를 탐색한다 |
| 명시 여부가 애매하거나 판단하기 어려움 | Human에게 폐쇄형 질문을 하고, 선택지에 "보류"를 포함한다 (DEC-050) |

- 라우팅을 위해 skill이 직접 다루지 않는 경우를 명시할 수 있다. 예: 데이터로 항목을 그룹으로 나누는 분석(군집화 등)은 이 skill이 다루지 않으며, 다른 Skill·Tool로 분석을 먼저 끝내고 Human이 관계 도식을 요청한 경우에만 이 skill을 쓴다. 분석 방법은 적지 않는다. (DEC-043, DEC-047)
- 분석에서는 그룹 개수를 먼저 묻고 → 분석하고 → 결과를 보고 이름을 추천한다. 분석 전에 이름·특성·배치 예시를 제시하지 않는다. 분석과 데이터 시각화가 산출물이며, 관계 도식은 Human이 요청할 때 whole_part로 그린다. 그룹 번호(인코딩 값)와 설명 이름은 다른 계층의 label이고, Human이 개수나 이름을 골라도 is_a 분류 체계가 되지 않는다. 표현을 위한 묶음은 먼저 그리고 사후 검토받는 별도 절차다. (DEC-039·040·041·044·094·102·143)

### 16.2 보류와 위임

- 폐쇄형 질문의 고정 선택지는 규칙 안의 답들과 "보류"다. "판단불가"는 선택지로 주지 않는다. 판단하기 어려운 상황은 해소할 대상이다. (DEC-050)
- "위임"(Agent가 정해 진행)은 꼭 필요할 때만, 검증 결과와 근거가 분명할 때만 선택지로 추가하며, 값과 근거를 함께 적는다. (DEC-051)
- Human이 보류하면 Agent는 결정을 돕는 설명을 더해 다시 묻거나, 위임 조건을 만족하면 결정한다. 풀리지 않은 보류는 그 부분을 그리지 않고 나머지만 산출하며, 미결로 기록한다. 기록에는 결정 주체(Human 결정 / Agent 위임과 근거·검증 / 보류와 다음 행동)를 적는다. (DEC-052, DEC-017 수정)
- 쌓인 보류는 그 Agent가 책임지고 줄인다. (DEC-053)
- Human의 보류는 결정 유보를 명시한 응답이다. 추가 설명 요청과 구분하고, 설명 뒤에도 해소되지 않은 판단불가는 미결정으로 기록한다. 질문·응답 없이 Human 상태를 추정하지 않는다. Agent의 검토 대기는 REVIEW 보고에만 남기며 Human 미결·후속 질문 목록에 넣지 않는다. 세부 처리와 위임 조건은 [human-decisions.md](../references/human-decisions.md)를 따른다. (DEC-116·121·122·126·129·135·136)
- Human이 요청하면 도식에는 표시하지 않고, 도식 밖에 무엇을 왜 그리지 않았는지 **글로 자유 서술**한다. 종류는 구분하지 않는다. (DEC-024)

### 16.3 질문 원칙

- 미결은 미결 목록을 READ한 뒤, 한 턴에 하나의 폐쇄형 질문과 장단점·상위 개념 설명으로 Human의 결정을 지원한다. (DEC-018)
- 폐쇄형 질문의 선택지는 기본 경로일 뿐 Human의 답을 제한하지 않는다. 선택지 밖의 답이 우선한다. (DEC-031, §1 해석 우선순위)
- Human이 고른 선택지가 Agent 권고였는지 함께 기록한다. (DEC-124)

### 16.4 고정 정책

- 고정 전에 미결을 최대한 없앤다. 고정 후 새로 발견되는 미결은 Human에게 질문하고, 선택지에 "보류"를 둔다. (DEC-005, DEC-050으로 수정)

### 16.6 skill 파일 구조

- skill은 `SKILL.md`(라우터·체크리스트), `references/`(Default 공통 규칙과 절차, 주제별 짧은 쪽: expression-rules·ir·information-amount·human-decisions·cli), `relation_types/`(execution_flow, goal_means, whole_part, is_a), `rules/`(Default가 아닌 세부와 수정용 전체 규칙), `scripts/`로 나눈다. 검증 후 필요하면 더 나눈다. (DEC-032, DEC-033)
- 모양과 의미의 대응은 각 관계 유형 파일에 둔다. `references/expression-rules.md`에는 모양 중립적인 규칙과 순위경쟁 규칙만 둔다. (DEC-034)
- skill에는 사람용 이력(작업 절차, 해결 목록, claim 추적표)을 넣지 않는다. (DEC-035)
- GoldenCase 과제 프롬프트는 실재하는 맥락(데이터·대상)을 갖춘다. 과제 결함으로 시험이 성립하지 않은 항목은 채점 불가(시험 불성립)로 보고 채점 분모에서 뺀다. (DEC-036)
- Default Case가 아닌 예외 Case의 Issue 대응은 `issue/`에 둔다. 번들 스크립트 결함은 `issue/script_defects.md`를 따른다: 스크립트는 고치지 않고 notes에 보고하며, 임시 대응은 IR 쪽에서만 한다. (DEC-037)
- 보류 처리(경우 2·3)는 판정표의 정규 경로이므로 `references/human-decisions.md`에 둔다. `issue/`는 문제가 생겼을 때의 대응만 담는다. (DEC-038)
- GoldenCase 평가 도구는 agent-eval-harness의 필수·권장 subtree를 커밋에 고정해 복사한 것을 쓴다. 복사한 원본 파일은 고치지 않고, 우리 설정·judge·dataset은 복사본 바깥에 둔다. (DEC-049)

### 16.7 완료 조건과 필수 확인 (문장 강화)

- 절차 준수는 먼저 **문장 강화만으로** 시험하고, 품질이 개선되지 않으면 그때 도구로 강제한다. (DEC-054)
- 완료 조건: 체크리스트의 모든 단계가 완료이거나, 미완료 단계마다 이유와 보류 기록이 있을 때만 완료다. 검증기의 통과와 종료 코드 0은 완료가 아니며, WARN이 남아 있으면 완료가 아니다.
- 의미 평가는 그리기 전과 렌더된 이미지 READ 뒤에 수행한다. 실제 내용의 요소·관계와 이미지가 표현한 뜻을 비교하고 대조표로 남긴다. 파일·줄·해시 등 경로의 존재나 일치를 의미 정합의 근거로 쓰지 않으며, CLI가 대조표 형식을 관문으로 강제하지 않는다. (DEC-137~140)
- 필수 확인: 경고 뒤 정보량 조정(접기 → 강조 측정 → 필요하면 Human 분할 질문), 이미지 READ(볼 수 없으면 PNG로 변환, 수단이 없으면 보류로 기록), IR을 고친 뒤 마지막 IR로 재검사·재렌더, 스크립트 오류 시 결함 대응 파일부터 읽기, HTML 요청은 정적 출력이 아님, 데이터 기반 분류는 데이터 시각화를 따로 냄.
