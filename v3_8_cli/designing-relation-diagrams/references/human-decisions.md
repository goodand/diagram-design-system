# 명시되지 않은 유형, Human 결정, 보류

**읽는 때**: 요청이 네 유형 밖이거나 판정할 수 없을 때(경우 2·3), `finalize`가 `STATUS REVIEW_PENDING`을 냈을 때, L0 동의를 받을 때, Human이 보류했을 때.

## 묶음 검토 (DEC-095·097·132·133·143)

1. 표현을 위한 묶음·추상화는 Agent가 먼저 정해 **L0을 먼저** 그려 Human 검토를 받은 뒤 L1을 그린다. L0에는 묶음이 접힌 상자로 보이므로 무엇이 어떤 이름으로 묶였는지 Human이 그림으로 판단한다.
2. `STATUS REVIEW_PENDING`: `source`가 `request`도 아니고 유효한 Human 결정(`human` + `decision_ref`)도 아닌 묶음은 막히지 않고 실선으로(점선은 원천이 미정이라고 표현한 경우만, DEC-141) 그리고, 검토 대기는 REVIEW 보고 글로 알린다 (DEC-133). 출력된 `REVIEW <group-id>` 블록(비교 그림 `candidates/index.html` 경로 포함)을 최종 보고에 그대로 넣는다.
3. Human 답을 `decisions.json`에 기록한다(형식은 [cli.md](cli.md)). "이대로 묶음"이면 `source:"human"` + `decision_ref:<결정 id>`, "묶지 않음"이면 IR에서 묶음을 뺀다, "보류"면 아래 보류 규칙.
4. 실제 Human 답이나 명시 요청 없이 `source`를 `human`/`request`로 쓰지 않는다. Agent가 정한 묶음을 Human이 승인한 것처럼 보고하지 않는다. 검토 대기는 REVIEW 보고에만 남기고 Human 미결 목록에 넣지 않는다(DEC-128·136).

## 경우 2 (명시되지 않은 유형)

- 요청의 **의미**가 모호하면 그리기 전에 Human에게 묻는다. 무엇을 기준으로, 몇 개로, 어떤 데이터로 그리는지 등을 확인한다.
- 의미는 분명하지만 이 skill에 **표현 방식**이 없으면, 다른 Agent Skill, Tool, GitHub repo를 탐색해 표현 방식을 찾는다. 찾은 방식과 출처를 notes에 적는다.
- 네 유형 중 하나로 억지로 끼워 넣지 않는다.
- **데이터로 그룹을 나누는 요청(군집화 등)**: 분석은 이 skill이 다루지 않는다. 분석 방법도 이 skill이 정하지 않는다. 다른 Skill·Tool로 **분석을 먼저 끝낸 뒤**, 그 결과를 도식으로 그릴 때 이 skill을 쓴다.
  - 순서: 그룹 개수를 먼저 묻고 → 분석하고 → 그 결과를 보고 그룹 이름을 추천한다.
  - 그룹 개수는 Human이 정한다. 개수 질문의 선택지는 숫자와 보류만 둔다(예: `3개` / `4개` / `보류`). 그룹 이름·특성은 분석 전에는 선택지에도 설명에도 쓰지 않는다.
  - 이 규칙의 목적은 **분석 편향 방지**다(DEC-094). 군집 개수·분할 개수 등 데이터 분석에서 정하는 모든 값에 적용한다: 분석 전에는 예시·이름·배치·그림을 보여 주지 않는다.
  - 나뉜 근거는 데이터 시각화로 보인다. **관계 도식만 내고 끝내지 않는다.** 데이터 시각화 파일을 따로 만든다.
  - 그룹 번호(인코딩 값)와 설명 이름은 서로 다른 계층의 label임을 밝힌다.
  - 분석 과제에서는 **분석과 분석을 위한 데이터 시각화가 산출물**이다. 관계 도식(L0·L1)은 그리지 않는다. Human이 요청하면 그때 데이터를 보고 나눈 것이므로 whole_part로 그린다(DEC-102).

## 경우 3 (애매하거나 판단할 수 없음)

- 상위 개념과 장단점을 설명하고 한 턴에 하나의 폐쇄형 질문을 한다. 선택지에 **"보류"**를 넣는다(DEC-018).
- 선택지는 기본 경로일 뿐이다. Human이 선택지 밖에서 답하면 그 답을 따른다.

## Human 응답과 검토 대기의 구분

- Human의 보류는 결정 시기를 유보하겠다는 명시적 응답이다. 추가 설명 요청을 보류와 같은 것으로 보지 않는다(DEC-116·118·126·129).
- 판단하기 어려워 추가 설명을 요청하면 설명을 보강한다. 설명 뒤에도 해소되지 않으면 미결정으로 기록한다(DEC-121). 추가 설명 요청은 판단불가를 알아보는 한 경로이며 그 정의 자체가 아니다(DEC-126).
- 질문·응답이 없는데 Human이 보류하거나 결정한 것으로 기록하지 않는다(DEC-122). Agent의 의도적 보류나 검토 대기는 Human 미결 목록과 구분한다(DEC-130·135·136).

## Human이 보류하면 (Agent의 책임)

- 보류를 줄이는 것은 Agent의 몫이다. 다음 중 하나로 진행한다.
  - 결정을 돕는 설명(이해를 돕는 풀이, 장단점)을 더하고 다시 묻는다.
  - 위임 조건을 만족하면 Agent가 결정한다.
- **위임 조건**: Human이 위임했을 때만 Agent의 위임 결정으로 기록한다. 위임 선택지는 꼭 필요할 때만, 그리고 검증 결과와 근거가 분명할 때만 제시한다. 위임을 선택지로 줄 때는 값과 근거를 함께 적는다(예: "추천값 3개로 진행 — 근거: 3개에서 오차 감소가 가장 크게 꺾임"). 값을 아직 계산하지 않았으면 위임 선택지를 넣지 않는다.
- 보류가 풀리지 않으면 그 부분은 그리지 않고 나머지만 산출하며, 미결로 기록한다. Human이 요청하면 도식에는 표시하지 않고, 도식 밖에 무엇을 왜 그리지 않았는지 글로 적는다.
- "판단불가"는 선택지로 쓰지 않는다. 판단하기 어려운 상황은 위 방법으로 해소할 대상이다.

## 기록에는 결정 주체를 적는다

Human이 고른 선택지가 Agent의 권고였는지도 보고에 남긴다(DEC-124). Human의 미결·보류에는 후속 질문과 다음 행동을 기록하고, Agent의 후속 작업 목록과 구분한다(DEC-117·123·135·136).

```
결정: Human — 3개
결정: Agent(위임) — 3개. 근거: …  검증: …
보류: 그룹 개수 — 다음 행동: 장단점 정리 후 재요청
```
